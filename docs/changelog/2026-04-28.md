## Updates

### ToolRouter benchmark results

We've published reproducible benchmark results that quantify the context savings of the [Tool Router](/core-concepts/tool-router) `search` strategy against real, connected MCP servers. The numbers confirm what the design promises: dramatic token reductions with negligible search latency.

Highlights from a live run with **128 tools across 6 MCP servers** (Supabase, Exa, Notion, DeepWiki, Neon, Zapier):

- **98.76%** initial token reduction vs. loading every tool schema upfront (3,571 tokens vs. 287,113).
- **96.80%** reduction even after the model discovers and pulls in three full tool schemas on demand.
- **Sub-millisecond** average search latency (p99 around 0.32 ms).

A smaller run with **60 tools** (Notion + Zapier) shows the same pattern: **97.99%** initial reduction and **94.84%** after three full schemas are loaded.

What this means for you:

- If you're connecting to large catalogs of MCP tools, the `search` strategy lets you stay well under typical LLM context limits without hand-curating which tools the model sees.
- Lower input-token counts translate directly into lower per-call costs on usage-based LLM APIs.
- Smaller, more focused tool contexts tend to improve model accuracy and reduce "lost in the middle" tool-selection errors.

See the [Tool Router](/core-concepts/tool-router) and [Meta-Tools](/core-concepts/meta-tools) guides for how to enable the `search` strategy in your app.
